## Summary

This change establishes the design system and bilingual user interface foundation for CareerCraft AI, introducing Tailwind CSS v4 semantic tokens, accessible Radix UI primitives, next-themes dark mode, and Next.js App Router subpath localization (`/[lang]`) for Arabic and English. The component architecture, Google Fonts integration, and logical CSS discipline are well implemented and clean. However, changes are requested due to an overbroad regex in middleware that hijacks valid two-letter application routes (such as `/cv` or `/me`) causing false 404 errors, alongside missing test coverage for middleware routing and core interactive components (`LanguageSwitcher`, `Dialog`, `DropdownMenu`).

## Major

### 🟠 Overbroad regex in middleware hijacks valid 2-letter routes, `src/middleware.ts:37`

**Problem**: The middleware checks `if (/^[a-zA-Z]{2}(-[a-zA-Z0-9]+)?$/.test(firstSegment))` to pass unsupported language codes through to the localized layout where `notFound()` is called. Because this regex matches any two-letter string, any unlocalized route beginning with a 2-letter segment (such as `/cv`, `/me`, `/ai`, `/in`, `/qa`, or `/hr`) is mistakenly treated as an unsupported locale instead of being redirected to `/${defaultLocale}/<path>`.
**Why it matters**: In CareerCraft AI, navigating to `/cv` or `/me` directly will return a 404 `notFound()` rather than redirecting to `/en/cv` or `/en/me`, silently breaking top-level routing conventions and causing unexpected dead ends for users.
**Suggested fix**: Avoid treating arbitrary 2-letter path segments as locale codes. Instead, maintain an explicit set or ISO lookup of language codes to reject/pass through, or let unlocalized paths always redirect to `/${targetLocale}${pathname}` so standard routes resolve properly within `/[lang]`.

### 🟠 Untested middleware routing and interactive foundation components, `src/middleware.ts:1` & `src/components/ui/components.test.tsx:1`

**Problem**: There is no test file for `src/middleware.ts`, leaving its cookie resolution, `Accept-Language` header parsing, 307 redirects, and path segment matching completely unverified by Vitest. Furthermore, `components.test.tsx` only tests `Button`, `Input`, `Textarea`, `Badge`, `Card`, and `RtlIcon`; it omits tests for `LanguageSwitcher` (explicitly mandated by AC-10), `ThemeSwitcher`, `Dialog`, and `DropdownMenu`.
**Why it matters**: Routing middleware is a critical gatekeeper for the entire application. Without regression tests, routing regressions or broken locale negotiation will easily escape to production undetected.
**Suggested fix**: Add `src/middleware.test.ts` covering root redirects, cookie overrides, header negotiation, and path handling. Expand `src/components/ui/components.test.tsx` to verify language switching behavior (cookie write and navigation) and component accessibility states.

## Minor

### 🟡 Trailing slash on root path redirect triggers secondary redirect, `src/middleware.ts:43`

**Problem**: When a user accesses the root path (`/`), the redirect URL evaluates to `/${targetLocale}/` (e.g., `/en/`). Next.js's default routing does not use trailing slashes and immediately issues an HTTP 308 redirect from `/en/` to `/en`.
**Why it matters**: This results in two sequential redirects (307 then 308) for every first-time visitor landing on `/`, adding unnecessary roundtrip latency.
**Suggested fix**: Normalize `pathname` when building `redirectUrl`: if `pathname === '/'`, map to an empty string so the resulting URL is `/${targetLocale}` instead of `/${targetLocale}/`.

### 🟡 Overbroad language tag matching in Accept-Language parser, `src/middleware.ts:17`

**Problem**: The header parser checks `if (lang.startsWith('ar'))` and `if (lang.startsWith('en'))`.
**Why it matters**: Non-Arabic or non-English language tags that share the two-letter prefix (such as `'arn'` for Mapudungun or `'arp'` for Arapaho) will erroneously match as Arabic.
**Suggested fix**: Validate language tags strictly against BCP 47 boundaries, e.g., `lang === 'ar' || lang.startsWith('ar-')`.

### 🟡 Language switcher drops query parameters and URL hashes, `src/components/ui/language-switcher.tsx:49`

**Problem**: `LanguageSwitcher` constructs `newPath` strictly from `usePathname()`, discarding `window.location.search` (`useSearchParams`) and hash fragments.
**Why it matters**: If a user switches languages on a page with filter query parameters (such as `?view=table&sort=asc`), all query parameters are lost upon locale change.
**Suggested fix**: Preserve `window.location.search` (or pass search params) and append it to `newPath` during `router.push()`.

### 🟡 Prettier formatting check failure across 4 files, `src/app/[lang]/design-system/page.tsx:1`

**Problem**: `npm run format:check` reports code style violations in `src/app/[lang]/design-system/page.tsx`, `src/components/ui/badge.tsx`, `src/components/ui/button.tsx`, and `src/components/ui/card.tsx`.
**Why it matters**: Violations of code style will fail the pre-commit hook (`lint-staged`) and CI checks.
**Suggested fix**: Run `npm run format` (`prettier --write .`) to resolve formatting differences.

## Test coverage

However, significant test gaps exist: `src/middleware.ts` has zero test coverage for its locale negotiation and redirect paths, and `LanguageSwitcher`, `ThemeSwitcher`, `Dialog`, and `DropdownMenu` have no automated test coverage in `components.test.tsx`.
