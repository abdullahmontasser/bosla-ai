# Review, main, 2026-10-25

**Reviewed by**: Gemini 3.8 Flash (spec review)
**Scope**: 1 spec file, docs/specs/0006-resume-parsing-and-ingestion/index.md
**Verdict**: Blocked (Resolved in spec update)

## Summary

This review assesses spec 0006 covering resume parsing and ingestion for CareerCraft AI. The spec defines a clean pipeline that extracts text locally in server memory using unpdf and mammoth, parses structured candidate fields with Vercel AI SDK generateObject using your active AI provider key, and presents an interactive review screen with section merge controls before committing to PostgreSQL. The architectural approach is sound and respects user privacy by avoiding permanent document storage. The initial verdict was Blocked because of one schema level blocker that will cause database insert crashes during extraction failures, alongside three major gaps around Next.js upload body limits, first time user onboarding without existing profiles, and undefined merge semantics for scalar fields. All findings were subsequently incorporated and resolved in spec 0006.

## Blockers

### 🔴 ParsedResume model requires non null rawText and parsedPayload during initial processing state, `docs/specs/0006-resume-parsing-and-ingestion/index.md:62`

**Problem**: The proposed `ParsedResume` model defines `rawText String` and `parsedPayload Json` as non null columns while having `status ParsingStatus @default(PROCESSING)`. When `parseResumeAction` starts or when a record is recorded, neither raw text nor parsed payload exists yet. If extraction fails before text extraction or JSON generation finishes, inserting or updating the database record requires fake placeholders like empty strings or empty JSON objects.
**Why it matters**: During normal file uploads, failures in early file inspection or timeouts during model calls leave the record incomplete. If non null columns cannot accept null, failed jobs cannot be recorded safely in PostgreSQL, breaking AC-6 error persistence.
**Suggested fix**: Make `rawText String?` and `parsedPayload Json?` nullable in the Prisma schema sketch. Add `updatedAt DateTime @updatedAt` to track job progress over time.
**Status**: Resolved. Made `rawText` and `parsedPayload` nullable and added `updatedAt` in spec 0006.

## Major

### 🟠 Missing Next.js Server Action body size limit configuration for 10MB file uploads, `docs/specs/0006-resume-parsing-and-ingestion/index.md:20` & `docs/specs/0006-resume-parsing-and-ingestion/index.md:93`

**Problem**: AC-1 and `parseResumeAction` accept uploaded files up to 10MB via a Server Action with `FormData`. Next.js App Router enforces a default Server Action body size limit of 1MB (`serverActions.bodySizeLimit`). Any file larger than 1MB uploaded through a Server Action will be rejected automatically by Next.js before the action function executes, returning an HTTP 413 error.
**Why it matters**: Real resumes commonly exceed 1MB, especially PDF files with embedded fonts or profile images. Without explicit configuration in `next.config.ts`, uploads between 1MB and 10MB will fail across all browsers.
**Suggested fix**: Add `serverActions.bodySizeLimit: '10mb'` to `next.config.ts` under the configuration required section and in the build plan.
**Status**: Resolved. Added Next.js serverActions bodySizeLimit 10mb configuration to AC-1, configuration required, and build plan.

### 🟠 Mandatory targetProfileId blocks first time users with no existing profile, `docs/specs/0006-resume-parsing-and-ingestion/index.md:95` & `docs/specs/0006-resume-parsing-and-ingestion/index.md:107`

**Problem**: `commitParsedResumeAction` specifies `targetProfileId: string` as a required input, and value sourcing states the parameter must be verified against an existing user profile in the database. When a brand new user uploads their first resume to bootstrap their account, they do not have an existing profile record in `profiles`.
**Why it matters**: A primary value proposition in user story 1 is populating a candidate profile without manual entry. Requiring an existing profile ID creates a dead end for new users who start by uploading a resume.
**Suggested fix**: Make `targetProfileId` optional (`targetProfileId?: string`). In the commit transaction, if no profile exists or if none is provided, automatically create a new `Profile` record with `isDefault: true` and link the child records to it.
**Status**: Resolved. Made `targetProfileId` optional and specified automated default profile creation for first time users in AC-5 and commit logic.

### 🟠 Undefined merge semantics for scalar profile fields and duplicate child entities, `docs/specs/0006-resume-parsing-and-ingestion/index.md:23` & `docs/specs/0006-resume-parsing-and-ingestion/index.md:108`

**Problem**: AC-4 and AC-5 define three merge choices per section (replace, append, skip). However, personal details consist of scalar columns (such as fullName, email, headline, summary), which cannot be appended. For child entities like skills and work experiences, the spec does not define how append handles duplicates or ordering.
**Why it matters**: If an implementer attempts to append personal info, the logic breaks. If an implementer appends skills or experiences on an updated resume, users will receive duplicate skill pills (like "React" twice) and colliding `sortOrder` values.
**Suggested fix**: Specify that scalar profile details support only replace or keep (or fill blank fields). For list sections like skills, specify case insensitive deduplication on name during append, and calculate `sortOrder` by taking the current maximum plus increment.
**Status**: Resolved. Added detailed merge semantics section covering scalar replace or skip rules, collection append sortOrder offsets, and skill name deduplication.

## Minor

### 🟡 DOCX files lack native page boundaries for the 10 page limit, `docs/specs/0006-resume-parsing-and-ingestion/index.md:20` & `docs/specs/0006-resume-parsing-and-ingestion/index.md:21`

**Problem**: AC-1 requires validating that files do not exceed 10 pages for both PDF and DOCX files. While PDF files have discrete page objects that `unpdf` can count via `getDocumentProxy`, DOCX files are XML archives with flowing text that do not contain fixed page counts without a layout rendering engine.
**Why it matters**: `mammoth` cannot count pages. Attempting to enforce a strict page count on DOCX will either fail or require heavy rendering dependencies like LibreOffice or Chromium.
**Suggested fix**: Enforce the 10 page limit on PDF files using `unpdf`, and enforce an equivalent character or word threshold (such as 10,000 words or 50,000 characters) for DOCX files.
**Status**: Resolved. Clarified PDF 10 page inspection via unpdf and DOCX 50,000 character volume boundary in AC-1 and build plan.

### 🟡 Build plan specifies **tests** folder violating repository testing rules, `docs/specs/0006-resume-parsing-and-ingestion/index.md:147`

**Problem**: Step 7 in the build plan proposes writing test files in `src/lib/parsing/__tests__/` and `src/actions/__tests__/`.
**Why it matters**: The repository rules in `AGENTS.md` explicitly mandate: "Tests: write unit tests using Vitest, placed beside implementation files with `.test.ts` extension". Using nested `__tests__` directories violates project convention.
**Suggested fix**: Update step 7 in the build plan to colocate tests next to source files, such as `src/lib/parsing/extract.test.ts` and `src/actions/resume-actions.test.ts`.
**Status**: Resolved. Colocated all proposed test files beside implementation files in build plan step 8.

### 🟡 Unclear boundary between non retryable extraction errors and retryable AI failures, `docs/specs/0006-resume-parsing-and-ingestion/index.md:94` & `docs/specs/0006-resume-parsing-and-ingestion/index.md:119`

**Problem**: `retryParsingAction` only accepts `parsedResumeId: string`. If parsing failed during document extraction (for instance, an encrypted or corrupt file), retrying the action with stored text is impossible because no text exists.
**Why it matters**: If the UI presents a generic retry button for all FAILED states, users who upload unreadable or scanned files will click retry and repeatedly receive extraction errors.
**Suggested fix**: Clarify that `retryParsingAction` applies only to AI provider failures where `rawText` is present. If text extraction fails, mark the record as FAILED with a distinct error code (`EXTRACTION_FAILED`) and instruct the UI to prompt for a new file upload.
**Status**: Resolved. Added distinct `errorCode` values (`EXTRACTION_FAILED` vs `AI_PROVIDER_ERROR`) to state transitions, schema, and API tables.
